# 工作原理

[简体中文](architecture.md) · [English](en/architecture.md)

面向使用者的完整讲解、数值例子、静态示意图和保证边界见 [压缩原理详解](principles.md)。本页用于代码导航。

## 从历史到下一步

Weave 在 DSH 的会话维护阶段整理上下文。一次压缩按以下顺序执行：

1. 读取当前消息表，测量输入规模，选出工具调用配对完整的历史区间。
2. 优先尝试保留已有检查点和稳定前缀，检查腾出的空间是否达到目标。
3. 从原始消息提取有效要求、近期原话和最新工作报告，建立来源引用。
4. 调用摘要模型生成候选；大段历史可分块，适用容量问题可进入后台分页接续。
5. 检查完整候选的结构、要求、进度与大小，失败时有限重试；合格后归档选区原文与附件。
6. 核验事务条件，备份并持久化替换，写入成功决定后发布检查点；后续对话从更新后的上下文继续。

常规多块流程逐块提交，后块失败时前块可能已经完成。分页接续保存已接受页面用于恢复，完整候选通过后才替换主历史。

## 缓存策略

`cache-policy.js` 优先选择最后一个检查点之后的历史区间。已有检查点和保留前缀维持原有内容，只在后面追加新摘要。

选择区间时同时考虑近期对话、摘要输出预算、原话预算、最新工作报告和最小释放空间。以下情况会切换到合并路径：

- 已达到 `cacheMaxCheckpoints`；
- 新要求修订了旧检查点携带的要求；
- 增量区间无法释放所需空间。

这样把前缀复用与上下文容量放在同一个决策里。服务端实际缓存量从模型返回的 usage 读取，测试记录单独展示压缩后的恢复过程。

## 要求与来源

`memory-policy.js` 处理要求的生效、修订、取消与去重。近期原话遵循条数和 token 预算，仍有效的要求独立保留。

`audit.js` 检查要求的覆盖、数值、否定、条件和适用对象。测试环境与生产环境、不同文件及不同批次分别判断。

原始事件号、文本片段和哈希共同标识来源。历史检查点中的生成文字不会成为新的原始要求；下一代压缩仍从经过核验的原始事件恢复依据。

独立的“继续”等低信息原话可以移出检查点。取消上一条时仍按原始用户消息顺序定位，避免因为裁剪改变指代对象。

## 进度与工作报告

`work-report.js` 保存最新工作报告的来源。短报告可随检查点携带原话，长报告保存来源标识，供后续摘要与回查使用。

`progress-facts.js` 跟踪有来源的文件数量、完成状态、产物路径和下一步。候选摘要的检查区分完成声明、引用历史、否定性提示和未来计划。

`0.3.2-rc.1` 的语义修复只改变候选摘要的解释方式，原始事实的提取、哈希、ID 与既有来源记录保持兼容。

## 分页接续与重试

完整摘要请求包含源消息、规则、近期原话索引和工作报告。`summary-budget.js` 按完整请求规划容量，`continuation.js` 在需要时分页生成工作笔记。

每个已接受页面保存来源身份和进度。重试或恢复时复用匹配的已完成页面，未完成页面继续请求。调用额度、实际发送与未知用量分别记录。

`summary-retry.js` 对超时、断流、空摘要、结构不合格和检查失败进行有限重试。常规和接续请求均使用 `singleTarget: true`，只请求选定的首个摘要目标。用户取消会结束当前操作。`summary-timeout.js` 在发送和读取阶段检查截止时间。

## 归档与提交

归档以消息区间组织，保存原始事件、消息块和工具关系。附件按 SHA-256 保存和校验，历史工具提供分段读取。

事务适配器对经审查的 DSH `0.2.2-rc.1`、`0.2.2-rc.2` 与 `0.2.2-rc.3` 宿主方法（含单条与批量 `Session.append` 实现）做指纹核验，按“备份、持久化替换、持久化成功决定、发布”的顺序提交；若遇到未知宿主方法实现则在摘要请求与历史修改前直接拒绝并保留已有恢复材料。成功决定前失败可恢复已核验的备份；决定后发布异常会隔离写入并要求冷重开会话，保留已持久成功的历史。

## 插件入口

`cordis.patch.yml` 注册配置入口，并让四种 preset 在入口就绪后加载。入口将 preset 中的基础压缩引擎替换为 Weave，合并原有配置与插件设置。

`client.js` 注册“摘要模型”设置页；`summary-config.js` 负责读取、校验和保存设置；`command-compact.js` 接入手动命令。
